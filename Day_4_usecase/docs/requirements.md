# Requirements

Requirements are grouped by capability. Each has acceptance criteria. See
[`domain-model.md`](domain-model.md) for the taxonomy referenced here, and
[`architecture.md`](architecture.md) for how each requirement is implemented.

## R1 — Domain-scoped query

**The user must select a therapeutic area and a regulatory jurisdiction before/with
every query.**

- Acceptance: a query cannot be submitted without both selections; the UI defaults to
  no selection (forces an explicit choice) rather than a silent default.
- Acceptance: selections are passed through the whole pipeline and are visible in the
  final answer (e.g. "Scoped to: Oncology / FDA").

## R2 — Multi-source retrieval

**The system retrieves evidence from three source categories: scientific literature
(PubMed/PMC, preprints), clinical trials (ClinicalTrials.gov), and regulatory documents
(FDA, EMA, ICH, PMDA, MHRA).**

- Acceptance: for a query where relevant evidence exists in more than one source
  category, the answer's citations include chunks from more than one category (not just
  whichever was retrieved first).
- Acceptance: retrieval is filtered by the domain selection from R1 — a cardiology query
  never returns oncology-tagged chunks; an FDA-scoped query never returns EMA-only
  guidance unless the user explicitly asks to compare jurisdictions.

## R3 — Claim-level citation

**Every sentence in a synthesized answer that asserts a fact must cite the specific
source chunk(s) it is grounded in, down to document + exact span + resolvable
source identifier (URL, DOI, NCT number, or application number).**

- Acceptance: a sentence with zero citations is rejected and regenerated by the
  pipeline before it reaches the user — this is enforced structurally (schema
  validation), not just by prompting.
- Acceptance: clicking/following a citation in the UI shows the exact source passage,
  not just the source document's title.

## R4 — Confidence judgment per claim

**Every claim carries a confidence tier (High / Medium / Low / Unverified) with a
human-readable rationale, computed from explainable inputs, not from an LLM's
unstructured self-report.**

- Acceptance: the rationale for a given confidence tier names the actual inputs that
  produced it (e.g. "3 independent sources, including 1 FDA label; verification
  check passed") — the same string a reviewer could recompute by hand from the
  scoring config.
- Acceptance: confidence scoring weights are stored in a config file a non-engineer
  can read, not hardcoded inside a prompt.

## R5 — Independent verification

**Before an answer is shown to the user, each claim is independently rechecked against
its own cited evidence for groundedness (does the cited text actually support the
claim as stated) — using a separate check from the one that generated the claim.**

- Acceptance: a claim that fails the groundedness check is not silently dropped; it is
  shown with an "Unverified" tier and the reason, or triggers a bounded retry against
  the Synthesizer before falling back to "Unverified."

## R6 — Evidence inspection

**The user can inspect the raw retrieved evidence behind any answer, independent of
the synthesized text.**

- Acceptance: an "evidence explorer" view lists every chunk retrieved for the query
  (including ones not ultimately cited), with source, similarity score, and metadata.

## Out of scope for this build

- Authentication, multi-user accounts, role-based access.
- Cloud hosting / horizontal scaling / production monitoring.
- Full-coverage ingestion of every jurisdiction's document catalog (seed sets only for
  EMA/ICH/PMDA/MHRA — see [`units-of-work.md`](units-of-work.md)).
- Formal statistical calibration of confidence scores (a reliability-diagram-style
  check is in scope for the POC; rigorous statistical calibration is not).

These are deferred, not rejected — see [`non-functional.md`](non-functional.md) for how
the architecture keeps them addable later without a rewrite.
